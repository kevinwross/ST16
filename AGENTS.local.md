## Definition of done

- [ ] Build clean: `dotnet build ST16.slnx --nologo` (Windows)
- [ ] Full suite green: `dotnet test ST16.slnx --nologo` (Windows)
- [ ] Off Windows, `dotnet build ST16.Portable.slnx` and `dotnet test ST16.Portable.slnx` are green
- [ ] Any change to behavior, a mnemonic, a fault code, or the binary format updates `docs/ST16-ISA.md` **and** `implementation.md`
- [ ] No new NuGet dependency without approval; `ST16.VM` stays free of external packages by design
- [ ] No secrets, debug output, or unrelated edits in the diff

The codebase is never left with failing tests. A task lands with the full suite green, not "green except the two tests I will fix later".

**The split that matters:** `ST16.slnx` includes the WPF GUI and builds only on Windows. `ST16.Portable.slnx` is the same solution minus `ST16.Gui` and `ST16.Gui.Tests`, so it builds and tests on Linux and ARM64. The two files must be kept in sync: a new portable project belongs in both, a Windows-only project in `ST16.slnx` only.

A Windows-only limitation anywhere outside `ST16.Gui` is a defect, not a design decision.

## Architecture boundaries

Dependencies flow downward; the reverse is forbidden.

- `ST16.VM` is the bottom layer and depends on nothing in this repository. It carries no UI code and no external packages.
- `ST16.Assembler`, `ST16.Disassembler`, and `ST16.CC` may depend on `ST16.VM`. They do not depend on each other except where the `.st16d` debug format is shared, whose single owner is `ST16.Assembler`.
- `ST16.App` composes the libraries and owns argument parsing and process exit codes.
- `ST16.Gui` depends on `ST16.VM` for debug hooks. `ST16.VM` must never reach into `ST16.Gui`, and each VM capability the GUI needs is exposed through an existing hook rather than a Windows-only path inside the VM.
- One executable: all functionality is reached through `st16` subcommands. Do not add a second entry point.

## Environment assumptions

- .NET 10 SDK, pinned in practice at 10.0.401. A different SDK band can change build output and analyzer behavior.
- Windows development also uses Visual Studio 2026 Community, but the `dotnet` CLI is the only required toolchain.
- Linux and ARM64 need only the .NET 10 SDK to build and test the portable subset. No WPF workload is available there and none is needed.
- `samples/build-all.ps1` requires PowerShell. On Linux or ARM64 use `pwsh`, or prefer the sample test project, which regenerates outputs itself.

## Known traps

- **`dotnet build ST16.slnx` fails on Linux and ARM64**, because the solution references the WPF project. Use `ST16.Portable.slnx` there, or the failure looks like a broken repository rather than an expected platform boundary.
- **`dotnet build` and `dotnet test` accept one project or one solution, not several project paths.** Naming multiple paths is parsed as MSBuild switches and fails. That is why `ST16.Portable.slnx` exists rather than a list of projects.
- **`docs/ST16-ISA.md` is frozen at v1.0.** Do not edit it to match the implementation. Fix the implementation. An intentional ISA change requires a v1.1 section, a changelog entry, and the user's agreement before the work starts.
- **`implementation.md` is the live per-phase record**, not history. When a phase's tasks or status change, update it in the same change; do not let it describe a state that has passed.
- **`plan.md` carries phase definitions of done.** Read the relevant phase before starting work in it; a change that satisfies the code but not the phase's stated deliverable is incomplete.
- **`ST16.VM` has no external packages by design.** Reaching for a NuGet dependency there, even an obvious one, needs approval first.
